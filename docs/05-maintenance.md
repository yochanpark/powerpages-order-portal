# 5. 유지보수

운영을 시작한 뒤 맞닥뜨린 장애·데이터 문제와 변경 요청, 보안 점검 대응이다.
원인을 끝내 특정하지 못한 것은 그렇다고 적었고, 시도했다가 되돌린 것도 남겼다.

## 운영에서만 나는 403 — 원인 추적과 우회

주문 목록에서 행을 눌러 상세 화면을 열면 폼이 비어 있었다.
페이지는 주문 한 건을 Web API(`/_api/{PREFIX}_digitalprintingorders(<id>)`)로 읽는데,
이 요청이 운영에서만 거부됐다.

```json
{ "error": { "code": "90040122", "message": "You are unauthorized to process this request." } }
```

**같은 코드가 개발 환경에서는 정상이었다.** 코드가 아니라 환경 차이라고 보고 권한 계층을 하나씩 확인했다.

| 확인한 것 | 결과 |
|---|---|
| 주문 행의 연락처 연결 | 정상 — 로그인한 연락처에 그 주문이 연결돼 있음 |
| 테이블 권한 | 있음. 범위를 연락처 → 전역으로 넓혀도 403 |
| 인증된 사용자 웹 역할 | 사이트에 연결됨. 웹 역할 중복 경고를 정리해도 403 |
| 필드 수준 보안 | 열 1개만 `$select` 해도 403 → 무관 |
| 포털 애플리케이션 사용자의 보안 역할 | 주문 테이블에 조직 범위 읽기 권한 있음 |
| Web API 사이트 설정 | `enabled: true` 확인 |
| 향상된 권한 부여 | 개발 환경도 꺼져 있음 → 차이 아님 |
| 세션 캐시 | 재로그인·사이트 재시작으로도 동일 |

**원인은 끝내 특정하지 못했다.** 대신 데이터를 읽는 경로를 Liquid 서버 렌더링으로 바꿨다
([1. 설계](01-design.md), 코드는 [2. 코드 작성](02-code.md)).

> Liquid `fetchxml`도 테이블 권한을 거친다. 그런데도 통과한 것은
> 막힌 지점이 권한 자체가 아니라 **Web API 경로**였다는 정황이다. 확정은 아니다.

## 2026-09-29 — 로그인은 되는데 화면이 깨진다

한동안 안 들어가 본 사이트가 깨져 있었다. 로그인은 되지만 주문확인 화면에 못 들어가고
헤더 드롭다운도 동작하지 않았다. 원인이 두 겹이었다.

**1. Web API 필드 와일드카드.** 관리 센터의 Site Checker가 경고를 띄웠다.

```
One or more Web API field site settings are configured with a wildcard (*)
  → Webapi/{PREFIX}_digitalprintingorder/fields
```

다른 테이블(거래처·연락처)은 필드를 나열해 뒀는데 주문 테이블만 `*`였다.
페이지 코드가 실제로 읽고 쓰는 열을 모아 쉼표로 나열한 값으로 바꿨다.

**2. CSP가 사이트 자신의 스크립트를 막았다.** 필드를 바꿔도 화면은 그대로였다. 콘솔에 이게 찍혔다.

```
Executing inline script violates the following Content Security Policy directive 'script-src …'
```

Studio의 CSP 화면에는 주소 검색용으로 추가한 외부 도메인(`t1.daumcdn.net`) 하나만 보였다.
그런데 실제로 적용되는 값은 사이트 설정 목록의 **`HTTP/Content-Security-Policy` 레코드**였고,
여기에 `'self'`·`'unsafe-inline'`이 빠져 페이지의 인라인 스크립트와 스타일이 전부 차단되고 있었다.

`'self'`와 `'unsafe-inline'`을 넣자 화면은 떴지만 **기능이 들쭉날쭉했다.**
콘솔을 다시 보니 플랫폼 도메인(`content.powerapps.com`)도 막혀 `$ is not defined`가 나고 있었다.
이것까지 넣어 복구했다(최종 값은 [4. 인프라](04-infra.md)).

> CSP를 직접 쓰는 순간 **플랫폼이 기본으로 허용하던 출처까지 내가 책임져야 한다.**
> 외부 스크립트 하나를 허용하려고 넣은 설정이 사이트 자신의 스크립트를 막을 수 있다.
> 바꾼 뒤에는 로그인·목록·상세·인쇄를 전부 열어 콘솔을 확인해야 한다.

같은 날 `HTTP/X-Content-Type-Options: nosniff`를 추가했다.

## 2026-10-01 — Web API 필드 목록 다듬기

필드를 나열하고 나서 저장할 때 403이 났다. 두 가지였다.

**누락된 열.** 페이지의 Liquid 조회·JS 저장 코드가 쓰는 열 5개가 목록에 없었다.
코드 세 군데(`<attribute name>`, Liquid 출력, 저장 payload)를 대조해 채웠다.

**대소문자.** 필드 목록은 대소문자까지 그대로 비교한다.
조회는 논리 이름(`{PREFIX}_account`), 저장 때 연결은 탐색 속성 이름(`{PREFIX}_Account@odata.bind`)을 쓰므로
**두 표기를 모두** 넣었다.

```
…,{PREFIX}_account,{PREFIX}_Account,{PREFIX}_contact,{PREFIX}_Contact,…
```

빠진 조회 열이 더 있는지는 코드를 뒤지는 대신 **테이블의 관계 목록**에서 확인했다.
사용자 지정 조회는 거래처·연락처 둘뿐이고 나머지(`CreatedBy`, `OwningUser` 등)는
시스템 열이라 포털에서 바인딩하지 않는다.

## 2026-10-01 — 거래처에 주문번호가 들어간 데이터

거래처 칸에 주문번호(`DI-####` 형태)가 들어간 주문이 발견됐다.
조회해 보니 포털이 잘못 보여준 게 아니라 **그 이름으로 거래처 레코드가 실제로 만들어져 있었다** —
등록 창의 회사명 칸에 주문번호를 입력한 것이다. 회사명 형식 검증이 없었다.
등록 경로 두 곳에 모두 검증을 넣었다([2. 코드 작성](02-code.md)).
신규 등록만 막으므로, 이미 잘못 만들어진 레코드는 따로 정리해야 한다.

## 첨부파일 방식 변경 — 시도했다가 되돌렸다

50MB를 넘는 파일만 링크로 따로 올리는 방식이라 고객사가 "두 번 일한다"고 해서
**용량과 상관없이 전부 SharePoint 링크로 올리는 방식**으로 통일하려 했다.

| 단계 | 결과 |
|---|---|
| 첨부 여부를 테이블의 실제 열(선택 항목)에 저장 | `true`를 보냈다가 400 — 이 열은 Boolean이 아니라 값이 정수 코드인 선택 항목이었다 |
| 외부 고객이 링크로 업로드 | 고객은 Microsoft 365 계정이 없어 **조직 SharePoint 폴더 링크로는 로그인 단계에서 막힌다** |
| 흐름에서 폴더만 만들고 공유 링크를 받기 | 흐름 트리거 스키마의 실제 키가 표시 이름과 달라(`text`, `text_1`…) 요청이 계속 스키마 불일치로 거부 |

포털의 클라우드 흐름 호출(`/_api/cloudflow/v1.0/trigger/<id>`)은 본문을 감싸는 방식과
트리거 스키마가 맞물려야 하는데, 이걸 맞추는 사이 기존에 되던 업로드까지 흔들렸다.
**첨부 부분만 원래 방식으로 되돌리고**, 같은 시기의 다른 변경은 유지했다.

> 교훈: 잘 되던 업로드 경로를 바꿀 때는 기존 호출 형태(본문 키·감싸기)를 먼저 기록해 두고,
> 새 방식은 **흐름 쪽을 먼저 단독 테스트**한 뒤 페이지를 붙였어야 했다.

## Site Checker 심층 스캔 — 항목별 판단

| 항목 | 위험도 | 판단 |
|---|---|---|
| 애플리케이션 오류 노출 | 낮음 | **조치.** 화면 디버그 영역의 요청 본문·응답·스택을 콘솔로만 옮기고 화면엔 일반 안내 문구 |
| `X-Content-Type-Options` 누락 | 낮음 | **조치.** `nosniff` 추가 |
| CSP: Wildcard Directive | 중간 | **수용.** CSP에 `*`는 없고 `default-src`가 없어서 뜬다. `default-src 'self'`를 넣으면 SharePoint 링크·외부 리소스가 막힐 위험이 크다 |
| CSP: `script-src 'unsafe-inline'` | 중간 | **수용.** 페이지마다 인라인 스크립트가 많아 빼면 사이트가 멈춘다(9/29에 실제로 겪었다). 고치려면 인라인 코드를 분리하고 nonce를 붙이는 리팩터링이 필요 |
| CSP: `style-src 'unsafe-inline'` | 중간 | **수용.** 위와 같은 이유 |
| 외부 도메인 스크립트(주소 검색) | 낮음 | **보류.** 스크립트를 웹 파일로 받아 자체 호스팅하면 CSP에서 외부 도메인을 뺄 수 있다 |

중간 위험도 3건은 모두 **고치려면 사이트 구조를 바꿔야 하고, 잘못 건드리면 사이트가 멈추는** 항목이다.
2차 방어선이 약한 것이지 그 자체로 뚫리는 취약점은 아니라고 보고, 구조 개선 일정으로 넘겼다.

## 남은 것

- 주문번호 확정 통보 흐름이 **거래처가 비어 있는 주문**에서 실패한다
  (`'recordId' … may not be null or empty`). 거래처 유무로 분기하려 했으나
  흐름이 managed 솔루션 소속이라 운영 환경에서 저장되지 않아 보류
- 통보 메일 수신자가 흐름에 **하드코딩**돼 있다. 채번 규칙은 설정 테이블로 뺐으면서
  수신자는 그러지 않아 일관되지 않다 — 담당자가 바뀌면 흐름을 고쳐야 한다
- 잘못 만들어진 거래처 레코드 정리
- 인라인 스크립트·스타일 분리 후 CSP 강화, 주소 검색 스크립트 자체 호스팅
