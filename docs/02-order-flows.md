# 2. 주문 자동화 흐름

주문 테이블에 붙은 Power Automate 흐름 둘이다. 둘 다 Dataverse 웹훅 트리거로 시작한다.

## 주문번호 채번

```
트리거: 행 추가/수정/삭제
  ↓
OrderType     (Compose)        트리거 행의 주문유형 열을 꺼낸다
  ↓
NumberConfig  (Dataverse)      채번 설정 테이블을 조회한다
  ↓                            ListRecords + $filter: 유형명 eq <OrderType>
조건          (If)             분기
```

핵심은 두 번째 단계다. **채번 규칙을 흐름에 하드코딩하지 않고
별도 설정 테이블에서 유형명으로 찾아온다.**

```
entityName: {PREFIX}_ordernumberconfigs
$filter:    {PREFIX2}_typename eq '@{outputs('OrderType')}'
```

주문 유형이 늘어나도 흐름을 고칠 필요가 없다. 설정 테이블에 행을 하나 추가하면 된다.

설정 테이블의 열 접두어가 주문 테이블과 다르다(`{PREFIX2}_` vs `{PREFIX}_`).
솔루션을 만들면서 게시자가 섞인 흔적으로, 조회식을 쓸 때 접두어를 확인해야 하는 이유다.

## 주문번호 확정 시 담당자 통보

```
트리거: 행 수정
        대상 테이블 = 주문 테이블
        필터링 특성 = 주문번호 열          ← 이 열이 바뀔 때만 발화
  ↓
거래처 ID 기준으로 행 가져오기  (Dataverse GetItem)
        accounts 테이블, 주문 행의 거래처 조회 열 값으로 조회
  ↓
메일 보내기 (V2)               (Office 365 Outlook)
```

**"행이 추가될 때"가 아니라 "주문번호 열이 바뀔 때"로 걸었다.**
트리거의 필터링 특성에 주문번호 열 하나만 지정해,
주문이 만들어지는 시점이 아니라 **채번이 끝난 시점**에 메일이 나간다.
다른 열을 고칠 때는 발화하지 않는다.

거래처명은 주문 행에 없고 조회(lookup) 열로만 있어서,
메일을 보내기 전에 `accounts`를 한 번 조회해 이름을 가져온다.

메일 본문은 인라인 스타일 HTML 표다. 주문 No. / 거래처 / 발주유형 세 줄을 담는다.
메일 클라이언트가 `<style>` 블록을 자주 지우므로 스타일을 태그마다 직접 붙였다.

> 수신자 주소는 흐름에 **하드코딩**돼 있다.
> 담당자가 바뀌면 흐름을 열어 고쳐야 한다.
> 채번 규칙은 설정 테이블로 뺐으면서 수신자는 그러지 않은 셈이라, 일관되지 않은 부분이다.
